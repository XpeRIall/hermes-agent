# Corrected Hermes Fork Architecture: Verified Substrate Composition Runtime

## Executive Summary

The earlier report got the main diagnosis right and the core staging wrong. It correctly concluded that Hermes already has a strong agent shell and a weak epistemic core: the runtime loop, prompt assembly, tool plumbing, skill UX, memory provider seam, background review, and session history/search are real assets, while durable learning is still mostly mediated by model judgement, free-form memory writes, transcript summarisation, and mutable `SKILL.md` documents rather than by typed evidence-backed state and promotion logic. That judgement remains sound. Hermes’ own code supports it: the system prompt is built as stable/context/volatile tiers and cached for session reuse; built-in memory is persisted in `MEMORY.md` and `USER.md`; only one external memory provider is allowed; provider prefetch is appended to the current user message; session search is FTS5 plus model summarisation; and background review can directly invoke memory and skill tools. [Sources: `/mnt/data/hermes_repo/hermes-agent-main/run_agent.py:6041-6266, 12489-12508, 12674-12690, 4325-4405`; `/mnt/data/hermes_repo/hermes-agent-main/tools/memory_tool.py:5-14, 221-230, 358-365`; `/mnt/data/hermes_repo/hermes-agent-main/agent/memory_manager.py:191-195, 204-230, 285-322, 330-375`; `/mnt/data/hermes_repo/hermes-agent-main/tools/session_search_tool.py:5-14, 325-337, 372-381, 421-451, 460-485`; `/mnt/data/hermes_repo/hermes-agent-main/tools/skill_manager_tool.py:5-12, 217-230, 444-454`; `/mnt/data/deep-research-report 3.md`, sections “Executive Summary”, “Current Hermes Architecture”, “Learning Mechanism and Provider Strategy”.]

What needs correction is the MVP conclusion. The previous report overcorrected toward “kernel-first minimalism” and, in doing so, pushed the **artifact/substrate architecture** too far down the roadmap. That would risk turning the fork into a narrower “verified memory + verified skills” system, which is not your stated goal and not the differentiator described in the architecture context. The context document is explicit that the stronger thesis is not merely typed state and safer skills; it is a **trusted kernel plus learnable, composable substrate**, where the agent can propose what lenses, schemas, projectors, evals, skills, tools, and adapters should shape a run, while the runtime validates and activates them. If that seam is absent early, the fork collapses back into a safer Hermes rather than becoming a verified substrate composition runtime. [Sources: `/mnt/data/chat_context_verified_agent_fork.md`, sections “Stronger thesis: verified cognitive substrate evolution”, “Trusted kernel vs learnable substrate”, “Dynamic substrate composition”; `/mnt/data/deep-research-report 3.md`, sections “Thesis Verification”, “Final Recommendation”.]

My corrected verdict is therefore: **the substrate composition architecture is valid and central, not optional garnish for later**. The MVP does not need the full artifact universe, but it does need the constitution of artifacts, trust states, an artifact registry, a `SubstrateActivationPlan`, a shadow-mode activator, and at least one real instance each of a `SkillArtifact`, `LensArtifact`, `EvalArtifact`, and `ContextProjectorArtifact`, plus a software-engineering domain pack v0. Without those, you cannot demonstrate the key thesis that the agent can safely assemble task-specific reasoning substrate rather than merely accumulate verified memories and instruction files. [Sources: `/mnt/data/chat_context_verified_agent_fork.md`, sections “Trusted kernel vs learnable substrate”, “Dynamic substrate composition”, “Software specialization”; `/mnt/data/hermes_fork_supplemental_source_pack_combined.md`, files `evaluation_criteria.md` and `example_task_traces.md`; `/mnt/data/deep-research-report 3.md`, sections “Phased Delivery Roadmap”, “MVP Definition”.]

The previous report was right to preserve Hermes rather than discard it. Hermes already contains several strong seams that are worth reusing in a fork: a mature runtime loop, a practical prompt assembly strategy, a real tool registry, structured skill discovery and editing, an external memory provider abstraction, background review hooks, and a SQLite-backed session database with FTS5 search and lineage support. Those are not trivial conveniences; they are the operator shell you want underneath a stricter kernel. It was also right to identify the epistemic failure mode. That is useful persistence, but it is not verified learning in the strong sense of evidence-backed, contradiction-aware, replayable, eval-gated state transitions. ## Where the Previous Report Over-Optimized for MVP

The main mistake was staging the artifact registry and substrate planner/activator too late. In the earlier roadmap, artifact registry arrived only after ledger, evidence, proposal-only learning, verified skills, and policy, and substrate planning/activation arrived even later. That sequencing would make the early fork prove only that Hermes can learn safer facts and safer skills. It would not prove the more important claim that the runtime can compose task-specific reasoning substrate from declared artifacts. In practice, that would bias implementation toward “memory plus skills” as the natural centre of gravity and make later substrate composition feel additive rather than foundational. [Sources: `/mnt/data/deep-research-report 3.md`, sections “Phased Delivery Roadmap”, “MVP Definition”; `/mnt/data/chat_context_verified_agent_fork.md`, sections “Stronger thesis: verified cognitive substrate evolution”, “Dynamic substrate composition”.]

The earlier report also over-read “don’t build the full artifact universe immediately” as “the artifact architecture itself can wait”. Those are different claims. It is correct to defer high-risk or speculative artifact types such as learnable policies, live model adapters, and broad self-mutating tools. It is not correct to defer the **constitution** that says substrate is made of artifacts with manifests, trust states, permissions, dependency rules, and activation records. If that constitution is missing early, the system has no structural place for lenses, projectors, and evals as first-class runtime elements, and the fork will ossify around memories and skills. [Sources: `/mnt/data/chat_context_verified_agent_fork.md`, sections “Trusted kernel vs learnable substrate”, “Dynamic substrate composition”, “Software specialization”; `/mnt/data/hermes_fork_supplemental_source_pack_combined.md`, files `evaluation_criteria.md` and `source_reliability_rubric.md`.]

A smaller but still important weakness was that the previous report understated **context projection** as a differentiator. The context document repeatedly warns against collapsing trusted claims, provisional hypotheses, provider synthesis, raw evidence, user preference, and active skills into one prompt block. Hermes today already shows why this matters: built-in memory and provider blocks are appended into prompt layers, and provider prefetch is injected into the user message at API-call time. If the fork does not establish `ContextProjectorArtifact` early, it cannot demonstrate that different epistemic categories are projected differently, which is one of the core reasons to build the fork in the first place. [Sources: `/mnt/data/hermes_repo/hermes-agent-main/run_agent.py:6212-6246, 12674-12690`; `/mnt/data/hermes_repo/hermes-agent-main/tools/memory_tool.py:11-14, 358-365`; `/mnt/data/chat_context_verified_agent_fork.md`, section “Context projection”; `/mnt/data/hermes_fork_supplemental_source_pack_combined.md`, file `evaluation_criteria.md`.]

## Corrected Thesis

**Decision:** the thesis is **valid and central**. It is not merely a later-stage refinement, and it is not invalid abstraction. The corrected thesis is that a real general-purpose learning agent is not a static prompt plus memory plus skills. It is a runtime in which the trusted kernel stays fixed while the task-shaped reasoning substrate is composed from validated artifacts. The reason this matters is not conceptual elegance. It is that broad task distributions demand different reasoning equipment: repo and symbol lenses for onboarding, failure-pattern and test evals for bugfixing, evidence-first projectors for research memos, graph/project adapters for long-lived operational memory, and so on. A runtime that cannot vary its substrate structurally will either hardcode too much domain logic or push too much responsibility back into one giant prompt. [Sources: `/mnt/data/chat_context_verified_agent_fork.md`, sections “User goal”, “Stronger thesis: verified cognitive substrate evolution”, “Dynamic substrate composition”, “Software specialization”; `/mnt/data/hermes_fork_supplemental_source_pack_combined.md`, files `example_task_traces.md` and `evaluation_criteria.md`.]

This does **not** mean the MVP must implement every candidate artifact type listed in the context. That full set remains too broad for early delivery. `PolicyArtifact`, `ToolArtifact`, `MemoryAdapterArtifact`, `AnalyzerArtifact`, `TransformArtifact`, and `ModelAdapterArtifact` are all real possibilities, but they are either high-risk, under-specified, or too dependent on later evidence. What must exist early is the **generic artifact seam** and a minimal set of concrete artifact types that prove composition is real. In the MVP, that minimal set is `SkillArtifact`, `LensArtifact`, `EvalArtifact`, and `ContextProjectorArtifact`, with claims and evidence handled by the kernel rather than by artifacts. [Sources: `/mnt/data/chat_context_verified_agent_fork.md`, sections “Trusted kernel vs learnable substrate”, “Dynamic substrate composition”, “Eval-gated self-improvement”; `/mnt/data/deep-research-report 3.md`, sections “Concepts Accepted / Modified / Rejected”, “Capability Artifact Model”.]

The strongest argument against the thesis is the risk of building a metadata-heavy framework that adds ceremony but little practical advantage. That objection is legitimate. The answer is not to abandon substrate composition; it is to make the early artifact model small, concrete, and visibly useful on real tasks. If a `LensArtifact` does not materially improve repo onboarding or Spark diagnosis, if a `ContextProjectorArtifact` does not materially improve epistemic separation, or if activation plans always converge to the same static set, then the thesis will have failed empirically. But that is a test of execution, not a reason to omit the architecture. [Sources: `/mnt/data/hermes_fork_supplemental_source_pack_combined.md`, files `golden_task_set_template.md`, `evaluation_criteria.md`, `example_task_traces.md`; `/mnt/data/chat_context_verified_agent_fork.md`, sections “What the final report should decide”, “Non-goals / things not to build first”.]

## MVP vs Architecture: What Must Exist Early

The corrected answer to your ten-item question is **yes, structurally, to all ten**—but with an important implementation distinction.

`CapabilityArtifact`, `ArtifactManifest`, trust/lifecycle states, `ArtifactRegistry`, `SubstrateActivationPlan`, and `SubstrateActivator` should exist in the MVP as real runtime components, not merely comments or future TODOs. However, the registry can be minimal, the activator can begin in shadow mode, and the number of live artifact types can stay narrow. The point is to establish that the runtime composes substrate through validated artifacts from the beginning. At least one real `SkillArtifact`, `LensArtifact`, `EvalArtifact`, and `ContextProjectorArtifact` should also exist in the MVP, because without them the registry and activator are only scaffolding. A software-engineering domain pack v0 should be present as the proving ground, because the stated usage mix is dominated by coding and repo work, and the supplemental evaluation pack explicitly frames coding bugfixes, repo onboarding, and dataflow/Spark diagnosis as golden task candidates. If the artifact runtime cannot improve those workflows, it has not proved its core value. [Sources: `/mnt/data/chat_context_verified_agent_fork.md`, sections “User goal”, “Software specialization”; `/mnt/data/hermes_fork_supplemental_source_pack_combined.md`, files `example_task_traces.md`, `golden_task_set_template.md`, `evaluation_criteria.md`.]

What should remain schema-only or deferred in the MVP are the riskiest or least-proven artifact families: dynamic `ToolArtifact` creation, `PolicyArtifact` learning, `MemoryAdapterArtifact` truth ownership, and `ModelAdapterArtifact` promotion into live reasoning. Those need the same artifact constitution, but they do not need full implementation in the first phases. In other words, the MVP should prove **artifact composition**, not **artifact maximalism**. ## Corrected Component Model

The corrected architecture has three layers, not two. First is the **trusted kernel**, which owns the run ledger, evidence store, typed claim store, policy engine, permission model, sandbox boundaries, artifact verifier, promotion gate, trust registry, and rollback/revocation rules. This layer is non-learnable under ordinary operation. Second is the **artifact constitution**, which defines what a capability artifact is, how it is manifested, versioned, trusted, activated, and revoked. Third is the **dynamic substrate**, which is the set of activated artifacts for a specific run. This third layer is task-shaped and can change per run; the second layer is the reason such changes remain inspectable and bounded. [Sources: `/mnt/data/chat_context_verified_agent_fork.md`, sections “Trusted kernel vs learnable substrate”, “Dynamic substrate composition”, “Run ledger and evidence requirements”, “Eval-gated self-improvement”.]

The minimal runtime flow should therefore be:

```text
user task
→ kernel creates run + ledger
→ planner proposes SubstrateActivationPlan
→ activator validates manifest, trust state, permissions, deps, eval status
→ activated substrate is logged
→ context projector compiles activation-specific context
→ model/tool loop runs inside that bounded substrate
→ outputs become evidence
→ extractor/dreamer may propose claims or new artifacts
→ promotion gate accepts, rejects, or leaves provisional
```

That flow is different from Hermes today. Hermes currently treats tool availability, memory provider context, skill usage, and project-context files as parts of a mostly static shell, while runtime-specific context is appended ad hoc to the user message. The fork should preserve the shell but insert activation as a first-class step before the first model call of each run. [Sources: `/mnt/data/hermes_repo/hermes-agent-main/run_agent.py:12489-12508, 12674-12690`; `/mnt/data/hermes_repo/hermes-agent-main/agent/prompt_builder.py:1417-1456`; `/mnt/data/chat_context_verified_agent_fork.md`, sections “Dynamic substrate composition”, “Context projection”.]

In practical MVP terms, the software-engineering domain pack v0 should provide one repo lens, one test/build eval, one coding skill, and one context projector that separates trusted project claims, provisional hypotheses, and raw evidence. That is enough to prove the substrate idea without pretending the runtime already learns the full universe of domain machinery. [Sources: `/mnt/data/chat_context_verified_agent_fork.md`, section “Software specialization”; `/mnt/data/hermes_fork_supplemental_source_pack_combined.md`, files `example_task_traces.md`, `golden_task_set_template.md`.]

## Corrected Delivery Phases

The corrected phase structure is better than the conservative one, but it needs one refinement: the artifact seam should start in **Phase 1**, not wait until Phase 3 conceptually, even if the first usable registry behaviour lands in Phase 3. In other words, Phase 1 should log activation-relevant events and introduce the base interfaces; Phase 2 should add evidence, claims, and proposals; Phase 3 should make activation real in shadow mode; and only then should the first concrete artifact families graduate into practical use. That sequencing keeps the architecture honest. ## Hermes Integration Points

The first crucial seam is inside `run_agent.py`, between Hermes’ current “turn started” notification and its current external-memory prefetch. At present, Hermes notifies memory providers of the turn, performs provider prefetch once, and then begins the model/tool loop. The fork should insert substrate planning and activation **in that slot**, because activation must happen before provider prefetch, prompt projection, and the first model call. Some activated artifacts will change what context is relevant, what providers may contribute, and what prompt overlays should exist. [Sources: `/mnt/data/hermes_repo/hermes-agent-main/run_agent.py:12489-12508, 12674-12690`; `/mnt/data/chat_context_verified_agent_fork.md`, section “Dynamic substrate composition”.]

The second seam is prompt assembly. Hermes currently builds a cached session prompt with stable/context/volatile tiers and only appends provider prefetch and plugin user context at API-call time. The fork should preserve that cached base prompt, but add an **activation overlay** compiled by the active `ContextProjectorArtifact`. That overlay should be per-run, not baked into the long-lived session cache, because substrate is task-specific and may change more frequently than identity or context files. In practice, the projector should compile category-fenced blocks—trusted claims, provisional hypotheses, evidence references, active skill guidance, and activated lens outputs—and inject them as an activation-specific overlay at API-call time. [Sources: `/mnt/data/hermes_repo/hermes-agent-main/run_agent.py:6041-6266, 12674-12690`; `/mnt/data/hermes_repo/hermes-agent-main/agent/prompt_builder.py:1417-1456`; `/mnt/data/chat_context_verified_agent_fork.md`, section “Context projection”.]

The third seam is the representation of current Hermes assets over time. `SKILL.md` packages should become `SkillArtifact` payloads with manifests and trust states. External memory providers should eventually be represented as `MemoryAdapterArtifact` instances, but only as optional adapters and not early canonical truth. Session search can remain a tool, but its results should become evidence objects rather than informal summaries only. The same pattern applies to provider outputs, tool outputs, test runs, file snapshots, and git metadata: they should feed the evidence store first, and only then claims or artifacts. [Sources: `/mnt/data/hermes_repo/hermes-agent-main/tools/skill_manager_tool.py:3-12, 217-230, 430-454`; `/mnt/data/hermes_repo/hermes-agent-main/tools/session_search_tool.py:333-337, 445-485`; `/mnt/data/hermes_repo/hermes-agent-main/agent/memory_provider.py:269-279`; `/mnt/data/chat_context_verified_agent_fork.md`, sections “Run ledger and evidence requirements”, “Provider strategy principle”.]

The fourth seam is activation logging. The run ledger should record at least four activation events: `activation_plan_proposed`, `activation_validated`, `activation_applied`, and `activation_denied_or_shadowed`. Without those, replay will still fail to explain why one run had a repo lens and another did not. Hermes’ existing session database is valuable, but it stores messages and session metadata rather than full causal execution decisions, so the new ledger must be parallel, not inferred later from `state.db`. [Sources: `/mnt/data/hermes_repo/hermes-agent-main/hermes_state.py:3-14, 190-240`; `/mnt/data/chat_context_verified_agent_fork.md`, section “Run ledger and evidence requirements”.]

## Provider Strategy Under Corrected Architecture

Honcho should be treated as **concept verification** for local dreamer and hypothesis generation, not as a truth layer. Hermes’ bundled Honcho integration makes that plain: it provides context injection, peer cards, dialectic reasoning tools, and persistent “conclusions”, and it even mirrors built-in user-memory writes into Honcho conclusions. That is exactly why it should remain advisory. The interesting part is not that Honcho stores memory; it is that it validates the usefulness of asynchronous persona synthesis and background memory reasoning. Under the corrected architecture, Honcho-like reasoning belongs behind the proposal boundary. [Sources: `/mnt/data/hermes_repo/hermes-agent-main/plugins/memory/honcho/README.md:25-40, 88-100`; `/mnt/data/hermes_repo/hermes-agent-main/plugins/memory/honcho/__init__.py:191-205, 497-555, 1153-1168`; `/mnt/data/chat_context_verified_agent_fork.md`, section “Honcho as concept verification”.]

Hindsight or other graph/project memory systems should be treated as later substrate adapters, not MVP-critical infrastructure. The Hermes plugin positions Hindsight as long-term memory with knowledge graph, entity resolution, and multiple deployment modes; that may become useful for project or entity-heavy recall later, but it is still not the kernel’s truth substrate. In the corrected architecture, a graph backend would enter as an optional artifact-backed adapter whose outputs are evidence or hypotheses unless separately promoted. [Sources: `/mnt/data/hermes_repo/hermes-agent-main/plugins/memory/hindsight/README.md:1-10, 114-120`; `/mnt/data/chat_context_verified_agent_fork.md`, section “Hindsight and Holographic hypotheses”.]

Holographic should be treated as seed code for local structured memory, not as the final claim store. Its schema is `facts`, `entities`, `fact_entities`, `facts_fts`, and `memory_banks`, with trust scoring and retrieval counts. That is useful local scaffolding, but it lacks the full claim/evidence/promotion model the fork needs. The correct role is therefore “prototype local structured store” or “migration bridge”, not canonical truth. [Sources: `/mnt/data/hermes_repo/hermes-agent-main/plugins/memory/holographic/README.md:1-16`; `/mnt/data/hermes_repo/hermes-agent-main/plugins/memory/holographic/store.py:16-49`; `/mnt/data/chat_context_verified_agent_fork.md`, section “Hindsight and Holographic hypotheses”.]

The governing rule should remain simple: **providers may emit evidence, summaries, hypotheses, or context suggestions; they do not define truth**. Under the corrected architecture, that rule becomes easier to enforce because providers can be represented as artifact-backed adapters whose activation, permissions, trust, and outputs are all mediated by the kernel. [Sources: `/mnt/data/chat_context_verified_agent_fork.md`, section “Provider strategy principle”; `/mnt/data/hermes_repo/hermes-agent-main/agent/memory_provider.py:1-9, 269-279`.]

## First Two Weeks

In the first two weeks, priorities should be reranked. The previous “ledger first, artifact registry later” ordering should be replaced by “ledger plus artifact seam immediately”. In week one, implement the run ledger skeleton, activation-related event types, `CapabilityArtifact`, `ArtifactManifest`, `ArtifactTrustState`, a minimal artifact table, and a `SubstrateActivationPlan` object. Also add the interception seam in `run_agent.py` so that every run can at least produce a shadow activation plan and log the result before the first model call. That is the earliest proof that the runtime is substrate-aware. [Sources: `/mnt/data/chat_context_verified_agent_fork.md`, sections “Proposed delivery path to verify”, “Dynamic substrate composition”; `/mnt/data/hermes_repo/hermes-agent-main/run_agent.py:12489-12508`.]

Still in week one, add the first four concrete artifact shells: one skill, one lens, one eval, one projector—initially as built-ins if necessary. For software engineering, the minimum viable set is a repo lens, a bugfix or onboarding skill, a test/build eval, and an epistemic projector. These do not need full learning loops yet; they do need manifests, trust states, and activation records. [Sources: `/mnt/data/chat_context_verified_agent_fork.md`, sections “Software specialization”, “Context projection”; `/mnt/data/hermes_fork_supplemental_source_pack_combined.md`, files `example_task_traces.md`, `golden_task_set_template.md`.]

In week two, add the evidence store, typed claim store, and proposal store; bridge the existing `memory` tool into claim proposals or typed updates; and make the context projector compile activated, category-fenced overlays rather than one blended memory block. If time permits, begin shadow-mode evals for the first coding tasks. If time does not permit, do **not** spend the remaining budget on provider integration or dreamer work; keep the focus on kernel truth and substrate activation. What should be present only as schema or seam during the first two weeks are `ToolArtifact`, `PolicyArtifact`, `MemoryAdapterArtifact`, and `ModelAdapterArtifact`. They should have reserved kinds and manifest support, but not active learning or broad runtime usage. That keeps the architecture general without taking on the highest-risk work immediately. ## Falsification Criteria

The thesis should be considered weakened or falsified early if substrate activation does not materially affect behaviour. If, after implementing the seam, nearly all useful runs choose the same static artifact bundle and task outcomes are no better than with a fixed software domain pack, then the “dynamic substrate composition” claim is probably overstated. In that case, the fork may still be worth building as a verified-memory and verified-skills runtime, but its broader architectural claim would be weaker than proposed. [Sources: `/mnt/data/hermes_fork_supplemental_source_pack_combined.md`, files `evaluation_criteria.md`, `golden_task_set_template.md`; `/mnt/data/chat_context_verified_agent_fork.md`, section “What the final report should decide”.]

The thesis should also be considered weakened if the artifact model becomes pure metadata with unclear operational value. Warning signs would include lenses that do not improve grounding, projectors that do not improve epistemic separation, evals that do not influence promotion or runtime safety, or activation plans that are so hand-wavy that they merely restate tool availability. In that scenario, the fork would be carrying abstraction cost without earning it. [Sources: `/mnt/data/hermes_fork_supplemental_source_pack_combined.md`, files `evaluation_criteria.md`, `example_task_traces.md`; `/mnt/data/chat_context_verified_agent_fork.md`, sections “Context projection”, “Eval-gated self-improvement”.]

A third falsification path is integration failure with Hermes itself. If the necessary seams in `run_agent.py`, prompt assembly, skill representation, and evidence capture prove so invasive that Hermes reuse no longer saves meaningful effort, then the balance may tip toward a cleaner runtime. The available code suggests this is not yet the case—Hermes has enough seams to justify a fork—but it is a real engineering checkpoint, not a theoretical one. [Sources: `/mnt/data/hermes_repo/hermes-agent-main/run_agent.py:6041-6266, 12489-12690, 4325-4405`; `/mnt/data/hermes_repo/hermes-agent-main/tools/skills_tool.py:9-12`; `/mnt/data/deep-research-report 3.md`, sections “Current Hermes Architecture”, “Final Recommendation”.]

## Final Recommendation

Yes, build priorities should be re-ranked. Keep the kernel-first discipline from the previous report, but move the artifact/substrate constitution into the **front** of the roadmap rather than the middle. The corrected MVP is not “Hermes plus ledger plus claims plus safer skills”. It is “Hermes plus trusted kernel **and** verified substrate composition seam”, implemented with a deliberately small initial artifact set. That is the architecture that matches the stated thesis and avoids silently collapsing back into a narrower system. [Sources: `/mnt/data/chat_context_verified_agent_fork.md`, sections “Stronger thesis: verified cognitive substrate evolution”, “Dynamic substrate composition”; `/mnt/data/deep-research-report 3.md`, sections “MVP Definition”, “Final Recommendation”.]

What must be implemented in the first two weeks is the run ledger, activation logging, `CapabilityArtifact`, `ArtifactManifest`, trust states, `SubstrateActivationPlan`, a shadow-mode activator, one skill artifact, one lens artifact, one eval artifact, one context projector artifact, and a software-engineering domain pack v0. That is the minimum set that proves the runtime both knows why it believes something **and** can change how it reasons for a task in a controlled way. [Sources: `/mnt/data/chat_context_verified_agent_fork.md`, sections “Run ledger and evidence requirements”, “Dynamic substrate composition”, “Software specialization”; `/mnt/data/hermes_fork_supplemental_source_pack_combined.md`, files `example_task_traces.md`, `evaluation_criteria.md`.]

What should remain schema-only or deferred is the broader artifact universe: learnable policies, live tool creation, memory adapters as truth owners, graph backends as canonical state, provider-centric truth, and live model-adapter mutation. Honcho-like dreaming should remain proposal-only when it arrives; Hindsight should remain optional later graph/project memory; Holographic should remain seed code or migration aid, not final epistemic storage. [Sources: `/mnt/data/chat_context_verified_agent_fork.md`, sections “Honcho as concept verification”, “Hindsight and Holographic hypotheses”, “Provider strategy principle”, “Non-goals / things not to build first”; `/mnt/data/hermes_repo/hermes-agent-main/plugins/memory/honcho/README.md:25-40`; `/mnt/data/hermes_repo/hermes-agent-main/plugins/memory/hindsight/README.md:1-10`; `/mnt/data/hermes_repo/hermes-agent-main/plugins/memory/holographic/store.py:16-49`.]

The blunt bottom line is this: the previous report was right about the shell, right about the kernel, and too conservative about the architecture. The MVP **must** include the substrate composition seam structurally from the start. Not because every artifact type needs to work on day one, but because without that seam there is no reliable path from “verified memory” to “verified cognitive substrate runtime” later. If you want the fork to justify itself as more than a safer Hermes, this is the correction that matters. It is lower-confidence on exact later-stage provider choices outside the bundled Hermes providers, because the supplemental source pack itself marks several external documentation sets as recommended-but-missing.
