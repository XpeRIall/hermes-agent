# Comparative Architectural Falsification Study of Hermes Fork Nova

## Executive verdict

The best-supported conclusion is **build a minimal substrate or promotion seam only**, not a full substrate runtime. The problem is real, but much narrower than the thesis at its most expansive. What appears missing across the inspected systems is not “a whole new cognitive substrate ontology.” It is a **governed write path for future-affecting reusable abstractions**: a way to propose, evidence, review, promote, scope, roll back, and blame persistent instructions or claims that will automatically influence later runs. Hermes itself has strong operator-shell machinery, but its persistent-learning semantics are still mostly flat memory, context injection, and mutable skills. [source-verified: `hermes-agent-main/agent/background_review.py`; `hermes-agent-main/tools/skill_manager_tool.py`; `hermes-agent-main/agent/memory_manager.py`; `hermes-agent-main/tools/checkpoint_manager.py`]

The architecture as proposed in the thesis is **only partly rational**. A narrow kernel is rational. The full architecture is not yet justified. The inspected systems already do a great deal of work in execution state, context retrieval, tool orchestration, permissioning, checkpoints, session persistence, and reusable packaging. Where they remain weak is not the read path or the execution path; it is the **governed promotion of future behavioral influence**. That gap supports a small experiment, not a cathedral. [source-verified: `hermes-agent-main/agent/prompt_builder.py`; `aider-main/aider/repomap.py`; `plandex-main/app/shared/data_models.go`; `plandex-main/app/cli/lib/rewind.go`; `OpenHands-main/openhands/app_server/event/event_service.py`; `OpenHands-main/openhands/app_server/app_conversation/app_conversation_service_base.py`; `crush-main/internal/workspace/workspace.go`; `codex-main/codex-rs/state/src/runtime/memories.rs`; docs-verified: `claude-code-main/examples/settings/settings-strict.json`; `claude-code-main/plugins/README.md`]

### Load-bearing evidence behind the matrix

Hermes context files are strong as static instruction injection but weak as a governed substrate. Hermes loads one project-context source by priority—`.hermes.md`, then `AGENTS.md`, then `CLAUDE.md`, then `.cursorrules`—and presents it as project context to be followed. That is prompt projection and static scoping, not promotion or evidence-backed learning. [source-verified: `hermes-agent-main/agent/prompt_builder.py`]

Hermes source is strong on operator-shell invariants but weak on governed writes. Its `CheckpointManager` transparently snapshots before mutating tool calls, lists diffs, and restores whole directories or a single file; its approval bridge exposes allow once, allow for session, allow always, and deny flows; and its skill system allows create, edit, patch, delete, and sidecar files. But background review explicitly says writes go directly to memory and skill stores, and the memory manager wraps recalled memory as “authoritative reference data.” That is precisely the overextension point: runtime safety is much stronger than epistemic safety. [source-verified: `hermes-agent-main/tools/checkpoint_manager.py`; `hermes-agent-main/acp_adapter/permissions.py`; `hermes-agent-main/tools/skill_manager_tool.py`; `hermes-agent-main/agent/background_review.py`; `hermes-agent-main/agent/memory_manager.py`]

Codex is strong on session state, persistence, approvals, sandbox defaults, and thread memories, but still not strong on governed artifact promotion. The thread metadata builder defaults to read-only sandbox and on-request approval. The thread store persists metadata such as sandbox policy, approval mode, dynamic tools, and memory mode. The memories subsystem persists stage-one outputs and can mark threads “polluted” when external context is involved. Built-in skills and AGENTS handling exist, but the inspected materials do not show evidence-backed promotion of reusable abstractions beyond summary-like memories and skill files. [source-verified: `codex-main/codex-rs/state/src/model/thread_metadata.rs`; `codex-main/codex-rs/state/src/runtime/memories.rs`; `codex-main/codex-rs/thread-store/src/types.rs`; `codex-main/.codex/skills/code-review-context/SKILL.md`; docs-verified: `codex-main/docs/agents_md.md`; `codex-main/docs/sandbox.md`; `codex-main/docs/skills.md`]

Crush is strong on sessions, permissions, LSP, MCP, and discoverable skill packaging. It persists multiple work sessions, tracks read files, lists session history, and exposes permission grant and deny methods. Its README documents permission allowlists, tool disabling, skill disabling, skill discovery from many directories, and project initialization that creates an `AGENTS.md`-style context file. None of that is a governed promotion layer; it is packaging, context, and runtime control. [source-verified: `crush-main/internal/workspace/workspace.go`; `crush-main/README.md`]

Aider is strong on context compression and narrow rollback, not on governed reusable promotion. `RepoMap` builds ranked repository maps; the repo layer auto-commits changes; and `/undo` can revert the last aider-made commit in safe cases. That is powerful operationally, but it governs code diffs, not future cognitive influence. There is no typed claim store or promotion gate in the inspected source. [source-verified: `aider-main/aider/repomap.py`; `aider-main/aider/repo.py`; `aider-main/aider/commands.py`]

Plandex is strong on plan state, diff review, branchability, and rewind. Its source models `CurrentPlanState`, `PlanApply`, `ContextsByPath`, apply, reject, reject-file, and rewind APIs; its config exposes modes from full auto to manual, including auto-apply, auto-exec, and auto-revert-on-rewind. This is unusually strong governance of **execution deltas** and plan state, but it is not the same as promotion of reusable cross-run cognitive substrate. [source-verified: `plandex-main/app/shared/data_models.go`; `plandex-main/app/shared/plan_config.go`; `plandex-main/app/cli/api/methods.go`; `plandex-main/app/cli/lib/rewind.go`; docs-verified: `plandex-main/README.md`]

OpenHands is strong on sandboxing, event persistence, and skill loading. The app server models sandbox information, persists events, and loads and merges skills from public, user, org, project, and sandbox sources into agent context. The user skill API parses markdown frontmatter and exposes metadata for global and user microagents. Again, this is reusable packaging plus event traceability, not evidence-gated promotion. [source-verified: `OpenHands-main/openhands/app_server/sandbox/sandbox_models.py`; `OpenHands-main/openhands/app_server/event/event_service.py`; `OpenHands-main/openhands/app_server/app_conversation/app_conversation_service_base.py`; `OpenHands-main/openhands/app_server/user/skills_router.py`]

That is a useful provider baseline, not evidence of a governed write layer. ## Missing-layer and redundancy analysis

The strongest candidate gap Hermes could fill is not memory, not retrieval, not traces, and not checkpoints. It is a **future-influence governance seam**: persistent objects that can change later behavior must be proposed, bound to evidence, reviewed, assigned a trust state, scoped, promoted, and later blamed or rolled back when they regress. In the inspected systems, runtime side effects are governed much better than cognitive side effects. [source-verified: `hermes-agent-main/acp_adapter/permissions.py`; `hermes-agent-main/tools/checkpoint_manager.py`; `plandex-main/app/cli/lib/rewind.go`; `OpenHands-main/openhands/app_server/event/event_service.py`; `codex-main/codex-rs/state/src/model/thread_metadata.rs`] 

That gap does **not** justify the full Hermes Fork substrate stack. Most of the thesis vocabulary is either already covered elsewhere in weaker form, or still too speculative to support first-class runtime embodiment.

## Minimal additive layer and kill criteria

### Smallest rational implementation

The candidate minimal set in the prompt does **not** survive intact. It should be reduced.

| Component | Keep now | Judgment |
|---|---|---|
| run ledger | **yes** | Necessary. It is the backbone for attribution of future influence. [inferred from inspected gaps] |
| evidence store | **yes** | Necessary. Promotions without evidence collapse into preference persistence. [inferred] |
| typed claim store | **yes** | Necessary. This is the smallest useful epistemic unit that is materially different from flat memory. [inferred] |
| proposal store | **yes** | Necessary. Background or autonomous learning should emit proposals, not trusted writes. [source-verified: `hermes-agent-main/agent/background_review.py`; uploaded thesis: `01_project_thesis/substrate_runtime_claims.md`] |
| artifact manifest or registry | **yes, but thin** | Keep only enough schema to know what is active, on what scope, and under what trust state. Do not build an ontology museum. [inferred] |
| trust states | **yes** | Keep a minimal enum such as `proposed`, `accepted`, `trusted`, `stale`, `rejected`. [inferred] |

### Strong hypothesis

A stronger and cleaner version of the thesis is:

> In repeated high-context software tasks on the same repository, a proposal-gated store of typed claims plus one promotable reusable artifact type reduces repeated mistakes and median debug time more than strong retrieval, traces, checkpoints, and evals alone, without raising per-task overhead enough to erase the gain.

A stricter operational version is:

> In task chains where the same latent repo-specific convention or failure pattern recurs, `ledger + evidence + typed claims + one promoted SkillArtifact`, optionally projected through a category-fenced context projector, will outperform `strong retrieval + traces + checkpoints + ordinary skills` on repeated-error reduction, regression attribution, and rollback usefulness. [inferred from the inspected systems and uploaded thesis]

### Kill criteria

| Condition | Interpretation | Action |
|---|---|---|
| retrieval, repo maps, checkpoints, and ordinary evals match the new layer on quality and repeated-error reduction | The problem is already solved well enough by read-path and execution-path tooling | **reduce to ordinary skills/memory or abandon** |
| `ledger + typed claims` matches or beats `ledger + typed claims + promoted artifact` | Governance matters, substrate activation does not | **stop at ledger and claims** |
| activation adds no measurable behavior change or the same bundle activates in almost every useful run | Dynamic substrate is fake adaptability | **replace dynamic activation with a static domain pack** |
| artifact manifests exist but do not alter context projection, permissions, procedure, or promotion | The artifact model is metadata-only | **merge into annotations or ordinary skills** |
| median overhead exceeds saved debug or rework time | The system is bureaucracy | **shrink or abandon** |
| promoted artifacts regress and the system cannot clearly attribute, demote, or quarantine them | Core promise failed | **stop autonomous promotion and simplify** |
| Hermes integration becomes invasive across the prompt builder, tool loop, and persistence layers without commensurate benchmark gains | The fork cost is too high | **use existing framework or keep this as a plugin-side governance layer** |
| an existing framework can implement proposal, evidence, gate, rollback, and activation more cheaply than the fork | Hermes is not the additive move | **use existing framework instead** |

These kill criteria are consistent with the uploaded adversarial pack, which already highlights the key falsifiers: retrieval may be enough, ledger and claims may be enough, dynamic activation may become static, artifacts may become metadata, and overhead may exceed value. ## Experiment design and final recommendation

### Benchmark design

Use **repeated high-context repository task chains**, not single-shot tasks.

The benchmark should use several real repositories and several task chains per repository. Each chain should contain at least one recurring latent abstraction, such as a build convention, a test harness quirk, a migration pattern, a naming rule, or a repo-specific debugging heuristic. A good chain is: repository onboarding, first fix, second related fix, refactor touching the same abstraction, then a repo change that makes the earlier abstraction partially stale, followed by a regression-fix task. That sequence tests discovery, reuse, staleness, demotion, and attribution.

The comparison arms should be exactly the user’s requested sequence, but with clearer implementation boundaries:

| Arm | What is enabled |
|---|---|
| baseline agent | strong context selection, repo maps or equivalent, normal traces, checkpoints, ordinary skills if the base framework already uses them |
| ledger plus typed claims | append-only run ledger, evidence store, typed claims, but no promoted artifact activation |
| ledger plus typed claims plus one promoted substrate type | same as above, plus one promotable `SkillArtifact` |
| optional seam arm | same as above, plus one `ContextProjectorArtifact` in shadow mode or lightly activated mode |

The benchmark should record:

| Metric | What it measures |
|---|---|
| quality | hidden tests, static analysis, and human review rubric |
| repeated-error reduction | whether the same class of mistake is repeated after first discovery |
| median debug time | time or turns from first failure to repaired passing state |
| overhead | extra turns, tokens, wall time, review actions, and artifact-maintenance cost |
| reuse across related tasks | whether a promoted item actually helps on later tasks in the same chain |
| rollback or demotion usefulness | whether stale or bad promotions can be cleanly removed with better subsequent performance |
| regression attribution | whether a bad later behavior can be linked to a specific promoted claim or artifact |
| activation specificity | whether task-relevant promotions are selected instead of broad context pollution |
| context pollution reduction | reduction in stale, unsupported, or mixed-trust prompt injections |

A decisive benchmark detail is to **intentionally invalidate** one earlier-discovered abstraction midway through each task chain. That forces the system to prove rollback and demotion value instead of only accumulating “wins.” Without that, the experiment will overstate the value of promotion and under-test stale state. [uploaded thesis: `01_project_thesis/concerns_and_kill_criteria.md`]

### Final recommendation

**Build minimal substrate or promotion seam only.**

Not the full substrate runtime. Not claims, lenses, analyzers, transforms, and projectors as a broad ontology. Not autonomous promotion. Not provider-mediated canonical truth.

Build:

- a run ledger,
- an evidence store,
- a typed claim store,
- a proposal queue,
- trust states,
- a promotion gate,
- rollback or demotion,
- one promoted `SkillArtifact`,
- one `ContextProjectorArtifact` in shadow mode.

Defer:

- `LensArtifact`,
- generalized `EvalArtifact`,
- dynamic multi-artifact activation,
- broad artifact taxonomies,
- analyzer or transform catalogs,
- provider truth adapters,
- any attempt to encode a full meta-cognitive runtime.

The strongest falsifying interpretation of the evidence is that **Hermes Fork is only justified if it becomes a narrow governed write layer for future influence**. If it becomes anything broader before benchmarks prove it, it is overbuilt.
