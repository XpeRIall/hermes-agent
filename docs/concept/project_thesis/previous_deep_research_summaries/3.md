# Hermes Fork Verified Learning Runtime Assessment

## Executive Summary

The fork is worth building, but not as “Hermes plus better memory”. The real justification is that Hermes already has a capable **agent shell** and a weak **epistemic core**. Its shell is strong enough to preserve: mature tool plumbing, a broad CLI/gateway surface, a useful skill system, built-in persistent memory files, SQLite-backed session history with FTS5 search, plugin/config loading, and practical background maintenance loops. Its learning core is not strong enough to trust for general-purpose cross-task learning, because persistence is still mostly direct LLM-mediated mutation of flat memory, transcript summaries, `SKILL.md` instructions, and provider-side conclusions/facts, without a run ledger, typed claims, evidence bundles, eval-gated promotion, contradiction handling, or rollback-first state transitions. That is an architectural mismatch with your goal. [Sources: repo/run_agent.py:1988-2087, 4269-4488, 5781-5890, 6041-6264, 12470-12715; repo/tools/memory_tool.py:5-24, 107-143, 221-264, 358-365, 512-579; repo/tools/session_search_tool.py:3-18, 325-538, 550-612; repo/tools/skill_manager_tool.py:3-20, 373-427, 430-790, 797-930; repo/agent/memory_manager.py:1-24, 190-249, 264-322, 483-555; repo/hermes_state.py:185-251, 253-306, 1686-1754, 1880-1960; /mnt/data/deep-research-report.md:5-10]

The correct interpretation of the thesis is therefore: **replace Hermes’ learning semantics, not Hermes’ operator shell**. The minimum defensible version is not the full proposed artifact taxonomy. It is a smaller kernel with six hard requirements: an append-only run ledger; an evidence store; a typed claim store; verified skill packages; a policy/runtime permission layer; and proposal-only background learning. Everything else, including generalised policy artifacts, model adapters, local fine-tuning loops, and broad substrate self-composition, should be deferred until the kernel exists and you can prove that state transitions are replayable and reversible. [Sources: repo/run_agent.py:4269-4488, 4490-4505, 6041-6264; repo/tools/skill_manager_tool.py:730-790; repo/plugins/memory/holographic/store.py:16-76, 146-190, 353-392; /mnt/data/chat_context_verified_agent_fork.md:91-160, 185-220]

My blunt verdict is this: **Hermes is operationally useful but epistemically weak**. The fork thesis is coherent, differentiated, and worth pursuing, but only if you explicitly reject the most over-abstracted parts of the current concept and build the kernel first. If you try to build the whole “capability artifact universe” immediately, you will likely create a large meta-framework that still cannot defend the correctness of what it learns. [Sources: repo/tools/memory_tool.py:515-536; repo/tools/session_search_tool.py:553-574; repo/tools/skill_manager_tool.py:799-828; repo/agent/memory_provider.py:1-31, 83-120; /mnt/data/deep-research-report.md:5-10; /mnt/data/chat_context_verified_agent_fork.md:116-160]

## Current Hermes Architecture

**Runtime loop.** Hermes initialises built-in memory, optionally loads a single external memory provider through `MemoryManager`, injects provider tool schemas into the tool surface, builds a cached system prompt, then runs an iterative model/tool loop. Before each API call it notifies memory providers of the new turn, prefetches external memory once, fences that prefetched context into the current user message, and then executes tool-call iterations until completion or iteration budget exhaustion. After the turn, it persists the exchange, mirrors it to external memory providers, and may spawn a background review agent that can mutate memory or skills. This is a real runtime, not a toy framework, but it has no run ledger separate from session history and no concept of proposal-vs-promotion for learned state. [Sources: repo/run_agent.py:2003-2087, 5791-5890, 6041-6264, 12489-12715, 15938-16103]

**Prompt assembly.** Hermes explicitly divides the system prompt into `stable`, `context`, and `volatile` tiers. Stable includes identity, tool-use guidance, skill-index metadata, and environment/platform hints. Context includes context files such as `.hermes.md`, `AGENTS.md`, `CLAUDE.md`, `.cursorrules`, and caller-supplied system messages. Volatile includes built-in memory snapshots, user profile snapshots, external memory provider prompt blocks, and timestamps. The resulting system prompt is cached for the lifetime of the agent instance to preserve upstream prompt-cache hits. This is a practical and strong design choice worth preserving. [Sources: repo/run_agent.py:6041-6264; repo/agent/prompt_builder.py:134-186, 988-1160, 1417-1456]

**Built-in memory.** Hermes’ built-in memory is a bounded, file-backed store with two files: `MEMORY.md` and `USER.md`. Those files are loaded at session start, deduplicated, rendered into a frozen system-prompt snapshot, and never refreshed in-prompt mid-session. Tool calls can `add`, `replace`, and `remove` entries; writes are protected by file locks and atomic renames. Hermes also scans new entries for basic prompt-injection and exfiltration patterns because the content will be reinjected into future prompts. This is competent engineering, but it is still a flat note store with no evidence model, no type system, no status lifecycle, and no explicit invalidation rules. [Sources: repo/tools/memory_tool.py:3-24, 62-104, 107-143, 221-356, 358-459, 512-579]

**Session search.** Cross-session recall is handled separately from built-in memory. The `session_search` tool uses SQLite FTS5 over the Hermes session database, resolves child sessions to their parent lineage, loads matching conversations, truncates around match regions, and then asks an auxiliary model to summarise the top sessions for the current query. That makes Hermes practically good at “what did we do before?”, but it remains transcript search plus summarisation; it is not a typed or replayable knowledge layer. [Sources: repo/tools/session_search_tool.py:3-18, 79-110, 113-196, 198-259, 325-538, 550-612; repo/hermes_state.py:185-251, 253-306, 1880-1960]

**Skills.** Skills are `SKILL.md` packages with YAML frontmatter and optional supporting files. Hermes supports progressive disclosure: `skills_list` returns compact metadata, `skill_view` loads full content, and `skill_manage` can create, patch, edit, delete, and manage supporting files. It validates frontmatter, enforces file path constraints, supports atomic writes, and optionally runs a security scan against agent-created skill content. Skills are real procedural memory and worth preserving, but they are still mutable markdown packages rather than versioned, manifest-driven, test-gated capability artefacts. [Sources: repo/tools/skills_tool.py:3-67, 86-105, 675-737, 850-919; repo/tools/skill_manager_tool.py:3-33, 50-102, 174-323, 373-427, 430-790, 797-930]

**Memory provider abstraction.** Hermes defines a narrow but sensible `MemoryProvider` interface: `initialize`, `system_prompt_block`, `prefetch`, `queue_prefetch`, `sync_turn`, `get_tool_schemas`, `handle_tool_call`, plus optional lifecycle hooks such as `on_turn_start`, `on_session_end`, `on_session_switch`, `on_pre_compress`, `on_memory_write`, and `on_delegation`. `MemoryManager` aggregates providers, enforces **one external provider at a time**, routes provider tool calls, and collects provider prompt blocks and prefetched context. This is a good seam for optional adapters, but not a sufficient seam for verified learning because it is deliberately provider-centric rather than kernel-centric. [Sources: repo/agent/memory_provider.py:1-31, 42-137, 142-200; repo/agent/memory_manager.py:1-24, 39-60, 173-187, 190-249, 264-322, 330-375, 376-555]

**Bundled provider integrations.** Honcho is implemented as an external provider with `context`, `tools`, and `hybrid` recall modes; it injects prefetched context into the user message, supports peer-card and dialectic tools, and mirrors built-in user-memory writes into Honcho conclusions. Hindsight is implemented as an external provider with cloud, embedded-local, and external-local modes, auto-recall, auto-retain, writer-thread serialisation, and `retain/recall/reflect` tools. Holographic is a purely local SQLite provider with FTS5 search, entity extraction, trust scoring, optional auto-extraction, and explicit fact tools. These are useful inspirations, but none of them acts as a canonical truth layer with evidence bundles, typed claims, or eval promotion records. [Sources: repo/plugins/memory/honcho/README.md:25-115, 130-177; repo/plugins/memory/honcho/__init__.py:191-345, 497-700, 1120-1318; repo/plugins/memory/hindsight/README.md:25-123, 136-138; repo/plugins/memory/hindsight/__init__.py:1060-1209, 1259-1510, 1566-1708; repo/plugins/memory/holographic/README.md:1-36; repo/plugins/memory/holographic/__init__.py:115-181, 183-255; repo/plugins/memory/holographic/store.py:16-76, 146-190, 191-351, 353-392]

**Background review and curator.** Hermes has two distinct maintenance paths. First, `run_agent.py` can spawn a **background self-improvement review** agent after a turn. That fork inherits the parent’s cached system prompt, is whitelisted to memory and skill tools, and can directly write to the same shared memory and skill stores. Second, the curator subsystem periodically reviews and archives or consolidates agent-created skills. Both mechanisms are genuinely useful operationally. Both also bypass the architecture you actually want, because they are direct mutation loops, not proposal-only evaluators. [Sources: repo/run_agent.py:4269-4488; repo/agent/curator.py:3-17, 257-322, 1369-1780]

**Persistence and state layout.** Hermes persists sessions and messages to `state.db` using SQLite, with tables for sessions and messages, FTS5 and trigram FTS tables for search, reasoning/codex fields in messages, lineage support through `parent_session_id`, and retry-oriented WAL-mode tuning. This is a strong base for session history, but it is not an append-only run ledger. The schema stores results, not all causal decisions. For example, it does not natively record policy decisions, permission diffs, evidence IDs, eval outcomes, or promotion state transitions as first-class entities. [Sources: repo/hermes_state.py:185-251, 253-306, 309-329, 744-918, 1686-1754, 1880-1960]

**Safety and plugin boundaries.** Hermes has real safety measures: plugin hooks are opt-in via config allow-lists; built-in memory scans stored text for injection/exfiltration patterns; skills can be security-scanned; dangerous command approvals exist; and context scraping is sanitised using `<memory-context>` scrubbers to avoid reinjecting remembered context as user input. These are worth preserving. However, they are not a capability-scoped policy runtime. They are pointwise guards around existing tools and prompt surfaces. [Sources: repo/hermes_cli/plugins.py:128-168, 196-223, 233-313; repo/tools/memory_tool.py:62-104; repo/agent/memory_manager.py:39-60, 62-170; repo/tools/skill_manager_tool.py:50-102]

**Deterministic vs stochastic.** Deterministic pieces: file persistence, schema validation, path guards, SQLite persistence, FTS5 search, provider routing, and prompt assembly structure. Stochastic pieces: what to remember, when to create or patch a skill, how past sessions are summarised, what provider-side user/project models infer, what background review decides to mutate, and how much recalled context is trusted by the model. Hermes is therefore a capable stochastic shell, not a verified learning runtime. [Sources: repo/tools/memory_tool.py:221-356; repo/tools/session_search_tool.py:198-259, 325-538; repo/tools/skill_manager_tool.py:730-790; repo/run_agent.py:4269-4488, 12470-12715]

**What to preserve in a fork.** Preserve the operator shell, tool registry, prompt-caching strategy, session database and FTS search, context-file loading, skill progressive disclosure, plugin discovery, and existing safety guards. Replace learning semantics, memory truth models, skill trust semantics, and background review mutation paths. [Sources: repo/run_agent.py:2003-2087, 6041-6264; repo/model_tools.py:175-199, 262-320, 688-790; repo/hermes_state.py:185-251, 1880-1960; repo/tools/skills_tool.py:675-737, 850-919]

## Learning Mechanism and Provider Strategy

**Learning mechanism assessment.** Hermes learning today is best described as **prompt-instructed artefact maintenance**. Built-in memory writes go straight into flat files. Session search returns transcript summaries, not typed state. Skills are editable markdown instructions. Background review can directly patch memory and skills. Provider writes can mirror user preferences or turn transcripts into external stores. There is no reviewed path that introduces typed claims with sources, no mandatory evidence bundle, no contradiction graph, no eval gate for persistent acceptance, no replayable promotion record, and no rollback-first state machine for learned artefacts. Blunt verdict: Hermes does not implement “verified learning”; it implements several useful LLM-mediated persistence conveniences. [Sources: repo/tools/memory_tool.py:515-536; repo/tools/session_search_tool.py:553-574; repo/tools/skill_manager_tool.py:799-828; repo/run_agent.py:4269-4488, 5832-5890; repo/plugins/memory/honcho/__init__.py:1153-1181; repo/plugins/memory/holographic/__init__.py:237-251]

**Provider strategy.** The right architecture is a split between a **canonical local substrate** and **optional provider adapters**. The canonical substrate should own the run ledger, evidence store, typed claims, contradiction handling, artefact manifests, eval results, trust state, and promotion records. Providers may contribute supplemental recall, summaries, user/persona synthesis, project/entity graph hints, or hypothesis proposals, but they should not define truth or perform direct trusted writes. That principle is directly aligned with the thesis developed in the prior architecture discussion, and it is the only way to use hosted or model-mediated systems without collapsing your trust boundary. [Sources: /mnt/data/chat_context_verified_agent_fork.md:91-160, 185-220; /mnt/data/deep-research-report.md:5-10]

**Honcho.** In Hermes, Honcho is strongest as **user/persona modelling and “background cognition” concept verification**. The provider deliberately separates context injection from tool usage, supports reasoning-oriented peer queries, peer cards, and persistent conclusions, and even mirrors user-memory writes into Honcho conclusions. That is useful, but it is still an external reasoning system with dialectic synthesis, not a verified claim layer. Recommendation: treat Honcho as concept verification and, later, as an optional adapter for persona/user-model hypotheses. Do not make it the canonical truth store. Self-hosting is only worth it if private user-modelling is strategically important early; it is not needed for the MVP kernel. [Sources: repo/plugins/memory/honcho/README.md:25-115, 130-177; repo/plugins/memory/honcho/__init__.py:275-345, 497-700, 1120-1318]

**Hindsight.** In Hermes, Hindsight is strongest as a **project/entity memory service**. It already thinks in banks, retention, recall, reflect, tags, and entity-aware memory. It also supports local embedded mode, which is relevant to a local-first roadmap. But it remains a provider-managed memory system with its own extraction and synthesis semantics. Recommendation: Hindsight is a sensible **optional later adapter** for project/domain recall or graph-like memory, especially if you want rich project/entity retrieval, but it should not be MVP-critical and should not own canonical state. [Sources: repo/plugins/memory/hindsight/README.md:25-123, 136-138; repo/plugins/memory/hindsight/__init__.py:1060-1209, 1259-1510, 1566-1708]

**Holographic.** Holographic is the most useful bundled provider for **seed code**, not for final architecture. Its strengths are local inspectability, SQLite, entity extraction, trust scores, FTS5, and explicit feedback loops. Its weaknesses are exactly the ones that matter for your fork: the schema is just `facts`, `entities`, `fact_entities`, and `memory_banks`; trust is a scalar; provenance is absent; scope and validity windows are absent; contradiction handling is heuristic; evidence bundles are absent; and no claim lifecycle exists beyond CRUD and trust adjustment. Recommendation: use it as seed code for a local evidence/claim subsystem, but replace it as the canonical substrate. [Sources: repo/plugins/memory/holographic/README.md:1-36; repo/plugins/memory/holographic/store.py:16-76, 146-190, 191-351, 353-392, 398-431, 474-520; repo/plugins/memory/holographic/retrieval.py:192-352]

**Mem0 and other alternatives.** Hermes’ bundled `mem0` provider, from the inspected code, is another provider-style memory backend with search/profile/conclude APIs and async sync/prefetch loops. That suggests the same general problem: it may be useful as an adapter, but it does not address the kernel requirements. For Zep, Graphiti, Letta/MemGPT, Cognee, LangGraph/LangMem, and LlamaIndex memory, I do not have primary-source verification in this run’s attached source pack, so I will not overstate specifics. My provisional judgement is still strong: none of those should become the canonical truth substrate unless they can own typed evidence, replayable promotion, and permissioned self-modification. In practice, that means they should all be treated as optional adapters until proven otherwise. [Sources: repo/plugins/memory/mem0/__init__.py:142-339; /mnt/data/hermes_fork_supplemental_source_pack_combined.md:202-218]

**Recommended split.**  
Use this split:

```text
Canonical local substrate
  - run ledger
  - evidence store
  - typed claim store
  - contradiction graph
  - capability artifact registry
  - eval results + promotion records

Optional adapters
  - Honcho: user/persona hypotheses and synthesis
  - Hindsight: project/entity recall and graph-like retrieval
  - Holographic: migration bridge / prototype local fact adapter
  - Others: non-canonical recall adapters only
```

That is the cleanest way to get local-first inspectability without throwing away provider leverage. [Sources: repo/agent/memory_manager.py:190-249, 264-322, 483-555; /mnt/data/deep-research-report.md:5-10; /mnt/data/chat_context_verified_agent_fork.md:91-160]

## Thesis Verification and Concepts Accepted Modified Rejected

**Is the thesis coherent?** Yes. “Agents learn by proposing and validating capability artefacts while a trusted kernel enforces evidence, replay, policy, sandboxing, provenance, and eval-gated promotion” is architecturally coherent. It is also differentiated from Hermes as-is, because Hermes currently has no such kernel, no artefact promotion state machine, and no canonical evidence/claim substrate. [Sources: repo/run_agent.py:4269-4488, 5832-5890; repo/tools/memory_tool.py:221-356; repo/tools/skill_manager_tool.py:730-790; /mnt/data/chat_context_verified_agent_fork.md:91-160]

**Is it over-engineered?** In its current broad form, yes. The full proposed artefact taxonomy is too wide for an MVP. `PolicyArtifact`, `ModelAdapterArtifact`, `MemoryAdapterArtifact`, `TransformArtifact`, and broad self-wirable analyser/policy stacks are all plausible future abstractions, but if you implement them now you will spend a long time building generalised metadata plumbing before you have solved the basic question of whether the system can learn safely at all. [Sources: /mnt/data/chat_context_verified_agent_fork.md:116-160; /mnt/data/deep-research-report.md:5-10]

**Accepted concepts.** The following concepts are valid and should survive:

- A **trusted runtime kernel** whose invariants are not self-modified by normal runs.
- A **proposal-first learning loop** rather than direct trusted writes.
- A **run ledger** as the main causal record.
- A **typed claim/project-state store** distinct from transcript search.
- **Verified skills** as permissioned, versioned, testable procedural artefacts.
- **Context projectors** that keep trusted claims, hypotheses, raw evidence, and persona synthesis epistemically separate.
- A **software-engineering domain pack** because coding will dominate actual usage.  
[Sources: repo/run_agent.py:6041-6264, 12470-12715; repo/tools/skills_tool.py:675-737, 850-919; /mnt/data/chat_context_verified_agent_fork.md:91-160, 185-220]

**Modified concepts.** The following ideas should be narrowed:

- The artefact taxonomy should begin with only five first-class types: `Claim`, `Skill`, `Eval`, `Lens`, and `ContextProjector`. `Tool` can remain static in Hermes initially, with permission manifests added before making it fully learnable.
- `PolicyArtifact` should not be genuinely learnable in the MVP. Policies can be proposed as drafts, but runtime enforcement rules should remain admin-owned.
- `ModelAdapterArtifact` should be offline-only at first. No live self-mutation, no automatic QLoRA promotion into production reasoning.
- `MemoryAdapterArtifact` should be an integration layer, not a truth layer. [Sources: /mnt/data/chat_context_verified_agent_fork.md:116-160; /mnt/data/deep-research-report.md:5-10]

**Rejected concepts.** The following should explicitly not be built yet:

- A universal, fully general “everything is an artefact” runtime from week one.
- Live self-training of reasoning models during ordinary operation.
- Automatic promotion of new tools or policies without explicit human approval.
- Provider-defined truth.
- Graph-first memory as the starting point.
- Attempting to solve all non-coding domains before software engineering is stable.
- Replacing Hermes with a plugin-only layer; the required changes cut through core runtime, persistence, tool dispatch, and review loops. [Sources: repo/run_agent.py:2003-2087, 4269-4488, 6041-6264; repo/model_tools.py:688-790; /mnt/data/hermes_fork_supplemental_source_pack_combined.md:67-97]

**Fork vs plugin layer vs new runtime.** A plugin layer is too small. A clean-room runtime is too expensive too early. The right move is a **Hermes fork with a new internal kernel**: preserve the outer shell, progressively replace the inner learning semantics, and keep clean boundaries so the kernel can later become more standalone if desired. [Sources: repo/run_agent.py:2003-2087, 4269-4488, 6041-6264, 12470-12715; repo/model_tools.py:175-199, 262-320, 688-790]

## Target Architecture

**Target Architecture.** The smallest defensible architecture is a trusted kernel that owns execution truth, while the agent only proposes persistent learning. The kernel should expose bounded extension points and treat all learned content as untrusted until promoted.

```text
TrustedKernel
  - RunLedger
  - EvidenceStore
  - ClaimStore
  - ArtifactRegistry
  - EvalRegistry
  - PolicyRuntime
  - PermissionBroker
  - PromotionGate
  - RevocationManager

RuntimeAdapters
  - Hermes tool registry adapter
  - Hermes session DB adapter
  - Legacy memory adapter
  - Provider adapters

LearningWorkers
  - Extractor
  - Dreamer
  - ArtifactFactory
  - ConflictResolver
  - EvalRunner
```

This keeps the core small and gives you a clear cut between trusted and learnable subsystems. [Sources: repo/agent/memory_manager.py:190-249, 264-322, 483-555; /mnt/data/chat_context_verified_agent_fork.md:91-160]

**Component Specifications.**  
The kernel should have these non-learnable responsibilities:

- event logging and replay control
- evidence identity and binding
- permission enforcement
- sandbox and side-effect boundaries
- artefact manifest validation
- eval-gated promotion
- state invalidation and revocation
- approval boundaries
- secret access policy

Extension points should exist only through manifests and capability-scoped APIs, never by allowing arbitrary learned code to rewrite kernel rules. [Sources: /mnt/data/chat_context_verified_agent_fork.md:93-114]

**Data Models and Schemas.**  
A minimal run ledger schema should look like this:

```json
{
  "event_id": "uuid",
  "run_id": "uuid",
  "session_id": "string",
  "turn_id": "uuid",
  "seq": 123,
  "ts": "2026-05-17T12:34:56.789Z",
  "kind": "user_input | prompt_snapshot | model_call | model_delta | tool_call | tool_result | file_read | file_write | provider_call | memory_read | memory_write | skill_read | skill_write | policy_decision | eval_result | claim_proposal | artifact_proposal | activation_plan | activation_result | final_output | error",
  "actor": "user | assistant | runtime | tool:<name> | provider:<name> | dreamer",
  "payload": {},
  "evidence_ids": [],
  "parent_event_id": null,
  "hash_prev": "sha256",
  "hash_self": "sha256"
}
```

Storage can begin in SQLite with append-only semantics and content-addressed blobs for large payloads; promotion to Postgres is warranted when you need multi-agent coordination or remote workers. This is materially different from Hermes’ current `sessions/messages` store, which is good history storage but not a causal ledger. [Sources: repo/hermes_state.py:185-251, 1686-1754; repo/run_agent.py:12470-12715]

The evidence store should bind all durable claims and artefacts to explicit evidence objects:

```json
{
  "evidence_id": "ev_x",
  "kind": "user_message | assistant_message | tool_output | file_snapshot | git_commit | test_result | benchmark_result | provider_output | external_doc | user_confirmation | user_correction",
  "source_ref": "path or session message id or commit sha",
  "content_hash": "sha256",
  "snapshot_uri": "blob://...",
  "anchors": {
    "file_path": "src/app.py",
    "line_start": 10,
    "line_end": 32,
    "symbol": "UserService.create",
    "branch": "feature/foo",
    "commit": "abc123"
  },
  "captured_at": "timestamp",
  "access_policy": "workspace/project/user scoped"
}
```

This is the crucial missing layer between Hermes’ flat memory and a verified runtime. [Sources: repo/tools/memory_tool.py:221-356; repo/tools/session_search_tool.py:325-538; repo/plugins/memory/holographic/store.py:16-76]

A typed claim store should replace direct flat-memory truth:

```json
{
  "claim_id": "cl_x",
  "type": "user_preference | project_fact | environment_fact | architecture_decision | coding_convention | tool_capability | invariant | failure_pattern | open_question | constraint",
  "scope": "user | workspace | project | repo | branch | session",
  "content": "Project uses pytest -n auto in CI",
  "status": "candidate | provisional | verified | trusted | stale | contradicted | revoked",
  "confidence": 0.82,
  "evidence_ids": ["ev_1", "ev_2"],
  "valid_from": "timestamp",
  "valid_until": null,
  "last_verified_at": "timestamp",
  "contradicted_by": [],
  "supersedes": null,
  "used_successfully_count": 14,
  "failed_count": 2,
  "invalidation_rule": "invalidate on pyproject.toml or CI config hash change",
  "owner": "workspace/project/user"
}
```

This gives you typed, testable state rather than stored prompt text. [Sources: /mnt/data/chat_context_verified_agent_fork.md:116-160]

**Capability Artifact Model.**  
Start with only these artefacts:

```text
SkillArtifact
LensArtifact
ContextProjectorArtifact
EvalArtifact
ClaimSchemaArtifact
```

Each should carry:

**Substrate Planning and Activation.**  
At runtime, the system should allow the agent to propose substrate activation, but activation itself must be deterministic:

```json
{
  "plan_id": "sap_x",
  "task_class": "bugfix | repo_onboarding | migration | design_doc | research | admin_workflow",
  "requested_artifacts": ["repo-lens@1.1", "pytest-eval@0.2", "python-bugfix-skill@0.5"],
  "requested_permissions": {
    "fs_read": ["repo/**"],
    "fs_write": ["repo/**"],
    "network": false,
    "shell": true
  },
  "expected_outputs": ["patch", "tests", "claim updates"],
  "evals_to_run": ["unit", "lint", "golden_bugfix_smoke"]
}
```

The **Substrate Activator** should validate manifests, dependency versions, trust status, eval status, and permission diffs before activation. The agent can propose; the runtime decides. [Sources: /mnt/data/chat_context_verified_agent_fork.md:185-220]

**Local Dreamer / Honcho-Like Cognition.**  
A local dreamer is worthwhile, but only as a **proposal engine**. It should never write trusted state directly. The right worker split is:

```text
DreamerWorker        -> cross-run patterns, repeated failures, recurring workflows
ExtractorWorker      -> candidate claims from user corrections, tests, commits, tool outputs
ConflictResolver     -> contradiction reports and stale-claim suggestions
ContextCompressor    -> compact summaries for prompt projection only
ArtifactFactory      -> draft skill/lens/eval proposals
EvalRunner           -> run draft artefacts on golden tasks
```

A Qwen 8B-class or similar local model is acceptable for this if it operates on logged evidence and emits proposals with evidence IDs. Adapter training should stay offline and out of the live trust path until you already have promotion records and rollback. [Sources: /mnt/data/chat_context_verified_agent_fork.md:91-160; /mnt/data/deep-research-report.md:5-10]

**Coding-Agent Domain Pack.**  
Because software work is the dominant use-case, the first serious domain pack should be software engineering. It should include:

- repo lens
- git lens
- symbol graph lens
- dependency graph lens
- build/test lens
- API/schema lens
- infra/IaC lens
- migration lens
- failure-pattern memory
- coding skills
- coding evals

All project claims must be anchored to repo snapshots, file/symbol anchors, commit hashes, and branch/worktree scope. If a file hash changes, claims that depended on it should become stale automatically. That is how you stop “project memory” from hallucinating across refactors. [Sources: repo/hermes_state.py:190-221; repo/agent/prompt_builder.py:1417-1456; /mnt/data/chat_context_verified_agent_fork.md:185-220]

**Security and Threat Model.**  
The main threats are memory poisoning, prompt injection persisted as memory, malicious skill patches, untrusted provider synthesis, permission escalation by learned artefacts, exfiltration through tools, poisoned evals, and stale self-reinforcing false claims. Hermes already shows why this matters: memory is reinjected into prompts, skills are executable guidance, providers can mirror writes, and background review can write directly. Your mitigations should therefore be: evidence binding; proposal-only learning; permissioned artefact manifests; human approval for elevated permissions; branch/file invalidation rules; eval provenance; trust revocation; and complete side-effect logging in the run ledger. [Sources: repo/tools/memory_tool.py:62-104; repo/tools/skill_manager_tool.py:50-102; repo/run_agent.py:4269-4488; repo/agent/memory_manager.py:39-60]

**Concurrency and Reliability.**  
SQLite is acceptable for a local-first MVP if you mirror Hermes’ existing discipline: WAL mode, retry-with-jitter, per-store locking, single-writer queues where needed, and append-only event logging. Hermes already does parts of this in `state.db`, Hindsight’s writer queue, and Holographic’s `RLock`. But once you have multiple long-lived agents, concurrent background learners, and promotion workflows, Postgres becomes the better home for the canonical substrate. My recommendation is: SQLite for phase-one local kernel, Postgres once you need multi-agent promotion and remote workers. [Sources: repo/hermes_state.py:309-329; repo/plugins/memory/hindsight/__init__.py:191-229, 1416-1491, 1694-1708; repo/plugins/memory/holographic/store.py:115-140]

## Final Recommendation and Appendices

**Final Recommendation.**

1. **Is the proposed architecture objectively defensible?**  
   Yes, if you reduce it to a kernel-first architecture and do not attempt the full abstraction set immediately. [Sources: /mnt/data/deep-research-report.md:5-10; /mnt/data/chat_context_verified_agent_fork.md:91-160]

2. **Which parts are invalid, weak, or over-abstracted?**  
   The full artefact taxonomy is over-abstracted for MVP. Fully learnable policy/model-adapter layers are too risky and too early. Provider-defined truth is invalid. [Sources: /mnt/data/chat_context_verified_agent_fork.md:116-160]

3. **Should this be a Hermes fork, plugin layer, or clean-room/new runtime?**  
   A Hermes fork with a new internal kernel. Plugin-only is too small; clean-room is too costly too early. [Sources: repo/run_agent.py:2003-2087, 4269-4488, 6041-6264]

4. **What should be preserved from Hermes?**  
   CLI/gateway shell, tool registry, session DB/search, prompt-caching strategy, context-file loading, skill UX, plugin/config plumbing, and existing safety guards. [Sources: repo/run_agent.py:6041-6264; repo/model_tools.py:175-199, 262-320; repo/hermes_state.py:185-251, 1880-1960]
