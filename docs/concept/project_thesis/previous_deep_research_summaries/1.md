# Hermes Fork Architectural Decision Report

## Executive summary

Forking Hermes is worth it, but not because Hermes already has the sort of rigorous, replayable, epistemically disciplined learning system you want. The source-grounded picture is that Hermes already has a strong outer shell: a mature CLI and gateway surface, a tool registry, built-in persistent memory files, SQLite-backed cross-session search, a self-managed skills system, a curator, and pluggable external memory providers. What it does **not** have is a formal learning substrate with typed claims, durable run-level provenance, eval-gated self-modification, or a policy model that scopes capability at the skill/runtime level. In its current form, “learning” is mainly LLM-mediated maintenance of artefacts: flat memory entries, `SKILL.md` procedures, session summaries, and provider-side conclusions or graph facts. citeturn7view3turn7view5turn13search7turn14search10turn8search12turn6view0

That means your proposed fork thesis is coherent, but only if you treat it as a **runtime-kernel replacement inside the Hermes shell**, not as a minor plugin or a memory-provider swap. The minimum defensible fork is: keep Hermes’ tooling surface, session search, security guardrails, and distribution ergonomics; add a Run Ledger, a Typed Epistemic State store, Verified Skills with manifests and tests, a Policy/Capability runtime, and an Eval Gate that turns background “self-improvement” into a proposal-and-acceptance workflow rather than blind persistence. citeturn14search10turn13search15turn17search2turn17search0turn17search11

On memory architecture, **Honcho + Hindsight is not enough by itself**. Honcho is a strong fit for user/persona modelling: peers, cards, conclusions, and dialectic reasoning are exactly that layer. Hindsight is a better fit for longer-horizon project/domain memory than Honcho because it exposes retain/recall/reflect and is explicitly a graph-and-entity-resolution memory system, with cloud and self-hosted modes. But neither system gives you a verified claim ledger, typed repo-anchored project state, or deterministic replay. For that, you still need a local, inspectable claim/evidence substrate and a separate run ledger. Holographic is useful as a **design seed** for a local store because it is inspectable and SQLite-based, but its present implementation is too heuristic and too weakly grounded to serve as your final verified-claims layer. citeturn9search12turn9search15turn9search9turn8search8turn10search0turn10search18turn10search8turn8search3turn8search1

My bottom-line recommendation is therefore: **fork Hermes, but keep the fork shallow at first**. Preserve Hermes’ operator surface and replace the learning core stepwise. Build the proof with local first-class ledger/state/skill verification before adding complex external memory infrastructure. Self-host Honcho only when you specifically need private, durable user modelling. Self-host Hindsight only once repo-anchored state and replay already exist and you can justify the operational overhead. Use Holographic as reference material, not as your final substrate. citeturn9search0turn9search21turn10search0turn10search14turn8search1

## Source-grounded map of Hermes today

### Confirmed implementation facts

Hermes’ built-in persistent memory is still a **flat, file-backed, curated memory system** with two stores: `MEMORY.md` for the agent’s long-term notes and `USER.md` for what it knows about the user. Those files are injected into the system prompt as a **frozen snapshot at session start**. Mid-session writes are durable on disk immediately, but they do not refresh prompt content until the next session, explicitly to preserve prompt-prefix caching. Hermes’ own docs also state that external memory providers run **alongside** built-in memory rather than replacing it. citeturn7view3turn2search2turn8search6

Cross-session recall is split between that curated memory and a separate **session search** subsystem. The `session_search` tool searches past transcripts in SQLite via **FTS5**, groups top matching sessions, loads the relevant session content, truncates around the match region, and then uses an auxiliary model to summarise those session slices for the main agent. That is valuable and practical, but it is still transcript search plus summarisation, not a typed or formally verified knowledge layer. citeturn7view5turn3search16

Hermes’ skills are procedural memory expressed as `SKILL.md` files with YAML frontmatter. The agent can create, update, and delete its own skills through `skill_manage`, and the skills docs explicitly frame this as Hermes’ self-improving procedural memory. The same docs show that skills are instructions that load into future sessions. Hermes also has a curator that performs background maintenance of agent-created skills, including staleness transitions and an LLM review pass that can keep, patch, consolidate, or archive skills. citeturn13search7turn13search2turn13search15

Hermes’ “self-improvement” loop is implemented as a **forked review agent** that runs after the response has already been delivered. Public docs state that memory and skill nudges fire on counters, with memory review on user-prompt cadence and skill review on tool-iteration cadence. The curator docs describe a similar forked-agent review pattern for skills. This is useful because it keeps the main turn responsive, but it also means learning writes happen on an auxiliary path rather than in a first-class, transactionally governed acceptance pipeline. citeturn14search10turn14search0turn13search15

The external memory provider abstraction is narrow and pragmatic. The repository’s memory-provider interface and manager show that a provider contributes a system-prompt block, prefetch context, turn sync, optional lifecycle hooks, and provider-specific tools. The manager routes tool calls to providers and explicitly enforces a **one-external-provider-at-a-time** rule to avoid tool-schema bloat and conflicting backends. The CLI docs say the same thing: one external provider can be active, while built-in memory stays on. citeturn6view0turn2search3turn8search12

Hermes does have real safety and ops machinery today. Skills installed from hubs go through a security scanner for exfiltration, prompt injection, destructive commands, and supply-chain signals. Hermes also documents dangerous-command approvals, environment passthrough constraints, and read-only credential mounting in containerised flows. That is meaningful value to preserve. At the same time, even Hermes’ own design discussion around skills notes that the current skill system has **no native tool restrictions, no requirements model, and no lifecycle binding to execution policy**, which is directly relevant to your fork thesis. citeturn17search0turn17search2turn17search3turn17search11

### Inferred end-to-end architecture

From the inspected source and docs, the current end-to-end flow is effectively this: a user message enters the runtime; Hermes assembles a large system prompt from identity/guidance plus frozen built-in memory and active skills; it adds tool schemas from the core registry and any active memory provider; it may prefetch provider context; then it runs an iterative model/tool loop, persisting the resulting turn into state and syncing built-in/external memory afterwards; finally, if counters fire, it may spawn a background review fork that proposes or directly writes memory/skill updates. That architecture is flexible and productive, but the “learning” happens mainly at the edges of the loop as artefact mutation rather than as typed state transitions in the loop’s core. citeturn7view3turn13search7turn14search10turn6view0turn7view5

The deterministic parts of today’s Hermes are mostly the mechanical ones: SQLite FTS search, file writes, trigger counters, and provider-manager routing. The stochastic parts are the important learning pieces: what to store in memory, whether a skill should be created or patched, how a provider synthesises user/project context, whether background review writes are actually improvements, and what old context still applies. That asymmetry is the core reason your fork thesis has substance. citeturn7view3turn7view5turn13search7turn14search10turn9search9turn10search8

### What Hermes is strong enough to preserve

Hermes is already strong enough in four areas that you should preserve rather than rebuild from scratch. First, the **operator surface** is valuable: CLI, gateway integrations, and multi-platform sessions are already mature. Secondly, the **tool registry and plugin model** are a good shell into which a new runtime kernel can be inserted. Thirdly, the split between **curated memory** and **session search** is conceptually right, even if the substrate is too weak for your end goal. Fourthly, the current security machinery—dangerous command approvals, skill scanning, and trust-gated plugin controls—gives you a non-trivial base layer that a greenfield runtime would otherwise have to rebuild. citeturn14search11turn14search16turn14search17turn6view0turn2search2turn3search16turn17search0turn17search2turn17search3

## Learning mechanism analysis and provider comparison

### How advanced the current learning implementation actually is

The current implementation is **more advanced than simple chat memory**, but it is still not “clear epistemics”. Hermes combines curated memory, transcript search, self-authored skills, background skill curation, and optional provider-side long-term memory. That is more ambitious than most agent shells. But the core learning mechanism is still predominantly: the model decides what matters, writes a flat or markdown artefact, and later another model decides whether to use or patch it. There is no repo-wide formal epistemic state with typed claims, confidence, evidence bundles, contradiction links, or validity windows. There is no documented global eval gate for persistent self-modification, and no first-class run ledger that would let you deterministically replay why a learned behaviour was accepted. citeturn2search2turn13search7turn13search15turn14search10turn6view0turn8search12

That gap is not theoretical; recent repo issues point at concrete failure modes created by the present design. A fresh `AIAgent` can be recreated on gateway turns, reinitialising providers and resetting self-improvement counters. The background review fork has had prompt-cache divergence issues, reasoning-config drift, and even reports of external memory pollution where internal review prompts were written into provider memory. There is also a recent issue requesting user confirmation because background self-improvement can create or overwrite skills autonomously. Those are exactly the kinds of “LLM-mediated maintenance” risks your fork is meant to remove. citeturn2search5turn14search3turn14search1turn14search7turn14search9turn14search5

The same is true for the claim substrate itself. Built-in memory is flat text. Session search is transcript search plus summarisation. Holographic gives trust scores and contradiction search, but only inside its own local fact store and with weak extraction heuristics. Hindsight and Honcho may be richer, but Hermes treats them through the same provider interface: prompt block, prefetch, sync, and provider-specific tools. That means Hermes today does not have a unified knowledge substrate in which claims, evidence, scope, confidence, verification status, and usage outcomes are first-class runtime objects. citeturn7view3turn7view5turn7view15turn8search1turn6view0

### Is Honcho plus Hindsight the right combination

It is the **best combination inside Hermes’ existing provider ecosystem**, but it is not “best in class” in the absolute sense, and it is not sufficient alone for your fork. Honcho is the best fit for user modelling because its abstractions are explicitly about peers, representations, cards, and conclusions. Hindsight is the best fit among Hermes’ shipped providers for richer project/domain memory because it is explicitly built around retain/recall/reflect, entity resolution, and knowledge-graph-like retrieval. If you want a two-provider story inside the current Hermes world, that is the least-wrong split. citeturn9search12turn9search15turn9search9turn8search8turn9search4turn10search18

But if the fork thesis is “verified skills + replayable runs + typed project state + policy-scoped execution + eval-backed improvement”, then **the actual winning split is broader**:

- **Honcho** for user/persona/interaction memory.
- **Hindsight or Graphiti** for project/domain graph memory.
- **Custom local verified-claims store** for typed, evidence-backed, repo-anchored state.
- **Run Ledger** for replay/diff/audit.
- **Skill Registry** for testable procedures.
- **Session Search** retained as episodic evidence lookup, not truth storage.

That split is more defensible because it maps each substrate to what it does best instead of asking one memory backend to be persona model, graph store, verified claim store, and run ledger all at once. citeturn9search12turn10search18turn1search10turn7view5turn6view0

### Fork-thesis critique

Your thesis is genuinely differentiated in three places. The first is **typed epistemic/project state**: Hermes does not currently expose a global substrate that lets the runtime say “this is a project fact, derived from this commit and this test run, still valid on this branch, last verified on this date”. The second is **deterministic/replayable runs**: Hermes persists sessions and memories, but not a complete ledger of prompts, model/provider versions, policy decisions, and accepted learning deltas. The third is **eval-gated self-modification**: Hermes currently improves itself by writing memory/skills through forked review flows; your thesis insists that durable updates need evidence, evals, confirmation, or at least provisional status. That is a real upgrade, not rebranding. citeturn2search2turn3search16turn13search7turn14search10turn14search5

The over-engineering risk is also real. If you try to ship Honcho, Hindsight, Holographic replacement, Graphiti experiments, a new skill runtime, policy engine, eval harness, and UI/workbench all at once, you will likely build an architecture diagram rather than a trustworthy agent. The minimum viable proof is much smaller: ledger first, typed state second, skill verification third, policy fourth, provider sophistication later. citeturn9search12turn10search0turn1search10

A plugin layer is **not** enough. Hermes’ own sources and design notes make clear that memory, skills, session search, and runtime review are wired into the core loop rather than cleanly isolated as optional middleware. The changes you want—run replay, policy enforcement around tool execution, acceptance-gated self-modification, and prompt projection from typed state—touch the runtime kernel. So this should be a **fork**, not an optional plugin pack. Over time it may become a mostly new kernel under Hermes’ UX shell, but beginning as a fork is the right move. citeturn6view0turn17search11turn14search10

## Target architecture for the fork

### Minimum defensible architecture

The minimum architecture that proves the thesis has six first-class components:

1. **Run Ledger**  
   Immutable event stream for every run.

2. **Typed Epistemic State**  
   Claims, evidence, constraints, decisions, open questions, failure modes, conventions.

3. **Context Projector**  
   Compiler from typed state into prompt-ready slices.

4. **Verified Skills Registry**  
   Versioned skill packages with tests, preconditions, permissions, and changelogs.

5. **Policy Engine**  
   Capability-scoped execution around tools, filesystem, network, repos, secrets, and budgets.

6. **Eval Gate**  
   Learning proposals enter here; nothing persistent is accepted without evidence, eval, user confirmation, or provisional labelling.

The important principle is that **memory providers become adjunct data sources**, not the sovereignty layer. The sovereignty layer is the ledger plus typed state plus skill registry.

A practical first schema can live in SQLite for local/single-user use, then move to Postgres when you need multiple workers and central audit.

Replay strategy:

- Reconstruct prompt snapshots and tool results from blobs.
- Re-run in **simulation mode** first, replacing side effects with recorded outputs.
- Re-run in **live verification mode** only for approved tools.
- Compute diffs on prompt, tool graph, file edits, produced artefacts, costs, and final answer.

This is the kernel missing from Hermes today.

### Typed epistemic and project state

Make claims first-class, not paragraphs in `MEMORY.md`.

```json
  "scope": {
    "owner": "user|workspace|project|repo|branch|session|global",
    "project_id": "proj-123",
    "repo_root": "/srv/app",
    "branch": "feature/authz"
  },
  "source": {
    "kind": "tool_result|file_anchor|user_statement|provider_memory|eval|git_commit|manual",
    "run_id": "uuid",
    "tool_call_id": "uuid|null",
    "file_path": "README.md",
    "line_start": 112,
    "line_end": 138,
    "symbol": "tests/pytest.ini",
    "commit_sha": "abc123"
  },
  "evidence_ids": ["evidence:1", "evidence:2"],
  "confidence": 0.88,
  "status": "provisional|accepted|deprecated|contradicted|expired",
  "validity_window": {
    "not_before": "timestamp|null",
    "not_after": "timestamp|null"
  },
  "created_at": "timestamp",
  "updated_at": "timestamp",
  "last_verified_at": "timestamp|null",
  "contradicted_by": ["claim:9"],

  "failed_count": 1,
  "access_policy": "project-maintainers",
```

This should be backed by a separate evidence table:

```json
{
  "id": "evidence:uuid",
  "kind": "file|tool_output|test_run|benchmark|user_confirmation|provider_record",
  "content_ref": "blob_id",
  "hash": "sha256",
  "run_id": "uuid",
  "commit_sha": "abc123",
  "created_at": "timestamp"

```

Projection into prompts should be **query-driven**, never full-dump. The projector should select:

- active invariants,
- branch-scoped decisions,
- repo conventions,
- relevant open questions,
- high-confidence user preferences,
- recent failure patterns with surviving validity.

That gives you epistemic compression rather than memory stuffing.

### Verified skills runtime

Current Hermes skills are useful but too loose: instruction documents, not executable contracts. Migrate to packages with a manifest and a content body.

```yaml
api_version: skills.v2
kind: SkillPackage
name: repo-test-fix
display_name: Repo Test Fix
version: 0.4.0
status: draft
review:
  signed: false
  reviewed_by: null
  last_verified_at: null

trigger_conditions:
  - "User asks to fix failing tests in a Python repo"
  - "Observed pytest failures in current run"

preconditions:
  - "Repo root detected"
  - "pytest available or installable"

postconditions:
  - "Target test command passes or failure is classified"
  - "Patch + rationale produced"

invariants:
  - "Never change production code without running relevant tests"
  - "Do not disable tests unless policy explicitly allows"

required_tools:
  - read_file
  - search_files
  - patch
  - terminal

permissions:
  filesystem: ["repo:read", "repo:write"]
  network: ["deny"]
  secrets: []
  git: ["status", "diff"]
  approvals:
    destructive_writes: require

inputs_schema:
  type: object
  properties:
    repo_root: {type: string}
    test_target: {type: string}

expected_artifacts:
  - patch.diff
  - test-report.json
  - explanation.md

examples:
  - input: "Fix failing auth tests"
    outcome: "Patched fixture ordering and reran pytest -k auth"

counterexamples:
  - "Do not use for flaky infra failures unrelated to repo code"

validation:
  commands:
    - "pytest -q"
  assertions:
    - "exit_code == 0"

rollback:
  instructions:
    - "git restore -SW ."
    - "revert patch from run ledger artifact"

changelog:
  - version: 0.4.0
    summary: "Added fixture-order failure pattern"

legacy_source:
  migrated_from: "~/.hermes/skills/repo-test-fix/SKILL.md"
```

Migration from the current Hermes format should be incremental:

- Existing `SKILL.md` becomes the package narrative body.
- YAML frontmatter seeds `name`, `description`, `tags`.
- Missing fields are auto-generated as `draft`.
- Legacy skills run in **compat mode** until they accumulate tests and permissions.

### Policy and permission runtime

Hermes already has approvals and install-time scanning, but you want a **unified execution policy**.

```yaml
policy_id: default-coding-policy
subjects:
  - "skill://repo-test-fix@0.4.0"
  - "run://interactive"
capabilities:
  filesystem:
    read:
      - "workspace://current/**"
    write:
      - "workspace://current/**"
    deny:
      - "~/.ssh/**"
      - "~/.hermes/.env"
  network:
    allow: []
    deny: ["*"]
  tools:
    allow: ["read_file", "search_files", "patch", "terminal"]
    deny: ["browser_*", "github_write"]
  secrets:
    allow: ["GITHUB_TOKEN:read"]
  budgets:
    max_tokens: 200000
    max_cost_usd: 5
  approvals:
    require_for:
      - "git push"
      - "rm -rf"
      - "network egress"
risk:
  default: medium
audit:
  denial_logging: true
```

Enforcement points:

- before tool dispatch,
- before skill activation,
- before file write,
- before network access,
- before secret materialisation,
- before provider writes,
- before persistent learning acceptance.

This is the place where a verified-skill runtime stops being “just better markdown”.

### Eval-driven self-improvement loop

Persistent updates should flow through a proposal model, not direct writes.

```json
{
  "proposal_id": "proposal:uuid",
  "kind": "claim_update|skill_patch|policy_change|state_invalidation",
  "proposed_by": "background-review|user|eval-runner|maintainer",
  "source_run_id": "uuid",
  "target_id": "claim:123",
  "diff_ref": "blob_id",
  "evidence_bundle": ["evidence:1", "evidence:2"],
  "required_checks": ["unit_tests", "golden_task_delta", "human_confirmation"],
  "status": "pending|accepted|rejected|rolled_back",
  "confidence_delta": 0.12
}
```

Acceptance rules:

- **Accepted automatically** only if evidence plus evals pass and policy allows.
- **Accepted provisionally** if evidence exists but eval is weak; prompt projector marks it provisional.
- **Accepted by human** where risk is high or change scope is large.
- **Rejected/rolled back** when regressions appear in later runs.

This is how memory, claims, and skills become accountable.

### Coding-agent-specific design

Because your dominant workload is software engineering, coding state must be repo-aware from day one.

Every coding-relevant claim or decision should carry:

- repo root,
- branch/worktree,
- commit SHA,
- file anchor,
- symbol anchor where possible,
- validation command linkage,
- last-seen hash of relevant files,
- stale-on-change invalidation rules.

Example:

```json
{
```

### Security and reliability model

For a local single-user fork, SQLite is still a sensible default substrate because it is transactional, embeddable, inspectable, and already a natural fit for ledger/state files. Hermes itself already uses SQLite with WAL and fallback handling, and SQLite’s own documentation makes clear it is a single-file transactional database that is excellent for embedded/local use. Where you expect **multiple agents and concurrent writers across machines**, move ledger/state to Postgres. citeturn15search0turn15search7turn15search6

Threat model priorities:

- prompt injection into memory or skill bodies,
- malicious skill content,
- policy escalation through skill updates,
- poisoning of user model,
- poisoning of project memory,
- secret exfiltration via tool calls,
- unreviewed autonomous self-modification,
- replay gaps that make regressions untraceable,
- concurrent update races on claims and skills.

Mitigations:

- all imported/provider-derived state enters as **untrusted evidence**, not accepted truth;
- no persistent skill patch without proposal + checks;
- deny-by-default network and secret policy for learned skills;
- run-level audit of every denial, approval, and accepted learning delta;
- optimistic version checks on claims/skills plus rollback records;
- crash-safe append-only events before side effects.

### What to build in the first two weeks

In the first two weeks, build only what proves or disproves the thesis.

**Week one**

- instrument a Run Ledger around model/tool/memory/skill operations;
- emit immutable `run_id`, `event_id`, `seq`, timestamps, provider/model/version, token/cost estimates;
- capture prompt snapshots before each model call;
- store tool inputs/outputs and file-change artefacts by reference;
- write replay tests for three real coding tasks.

**Week two**

- add a minimal Typed State store with `claim`, `evidence`, `proposal`;
- bridge the existing memory tool so `memory(add)` creates provisional claims instead of flat-only entries;
- convert background self-improvement into **proposal emission only**;
- require either user confirmation or a simple eval pass before accepting new skill/memory state.

If those two weeks do not materially improve replayability, debuggability, and stale-memory handling on real coding tasks, the broader fork thesis is probably not worth the added complexity.

## Final recommendation

### Clear decisions

| Question | Recommendation |
|---|---|
| **Should you fork Hermes or build separately?** | **Fork Hermes.** A plugin layer is too weak; a greenfield rewrite throws away too much useful shell. Treat the fork as “Hermes UX + new learning kernel”. |
| **Should you self-host Honcho?** | **Eventually yes, but not for MVP.** Use it when you specifically want private/user-model continuity across profiles and sessions. |
| **Should you self-host Hindsight?** | **Not at first.** Do it only after local ledger/state works and you know you need shared graph/project memory badly enough to pay the ops cost. |
| **Should you keep Holographic?** | **Do not keep it as the primary truth store.** Reuse its inspectability ideas; replace it with a better typed local claim store. |
| **Minimum viable architecture that proves the thesis?** | Run Ledger + Typed Claims/Evidence + legacy-memory bridge + proposal-only background review + basic skill manifest sidecar + policy wrapper. |
| **Strongest long-term architecture?** | Hermes shell + local ledger/state/skills/policy core + Honcho for user model + Hindsight or Graphiti for domain graph + eval gate governing all persistent learning. |

### Pressure points that justify the fork

| Pressure point | Why it is a valid fork argument |
|---|---|
| **Learning is background artefact mutation, not typed state transition** | Hermes’ self-improvement loop is a forked review agent that writes memory/skills after threshold triggers, which is helpful but not a formal epistemic runtime. citeturn14search10turn13search15 |
| **Built-in memory is flat and frozen per session** | `MEMORY.md` and `USER.md` are file-backed snapshots injected once per session; mid-session updates do not update prompt state. citeturn7view3turn2search2 |
| **Session search is episodic search, not knowledge state** | It is SQLite FTS5 plus auxiliary summarisation, which is strong recall but not typed/project-aware truth. citeturn7view5turn3search16 |
| **Skills are documents, not verified capabilities** | Hermes’ skill system is `SKILL.md`-based procedural memory, and current design notes explicitly say it has no tool restrictions/requirements/lifecycle binding. citeturn13search7turn17search11 |
| **Only one external memory provider can be active** | That makes it hard to cleanly separate persona memory, graph memory, verified claims, and episodic evidence. citeturn6view0turn8search12 |
| **Background review can drift from the parent runtime** | Recent issues document prompt-cache divergence and reasoning-config mismatch in the review fork. citeturn14search1turn14search9 |
| **Background review can pollute provider memory** | There is a recent bug report showing review prompts written into external memory providers such as Honcho. citeturn14search7 |
| **Gateway lifecycle can starve or distort learning** | Fresh agent construction can reset memory-review counters and reinitialise providers across messages. citeturn2search5turn14search3 |
| **Holographic is insufficient as verified truth** | Its local design is appealing, but the current auto-extract path can store raw conversational snippets as “facts”. citeturn8search3turn8search1 |
| **Current autonomous skill writes lack strong acceptance controls** | There is already a user-facing issue requesting confirmation because background self-improvement can create or overwrite skills without explicit approval. citeturn14search5 |

### Top implementation risks

| Risk | Consequence | Mitigation |
|---|---|---|
| **Overbuilding too early** | You spend months on architecture without improving agent quality | Start with ledger + typed claims only |
| **Schema churn** | Claims and skills become unstable before they are useful | Version schemas from day one |
| **Policy overconstraint** | Agent becomes safe but useless | Begin with audit-only mode before hard enforcement |
| **Replay incompleteness** | Ledger exists but cannot explain failures | Log prompt snapshots and tool artefacts first |
| **Provider lock-in** | State becomes entangled with Honcho/Hindsight internals | Treat providers as evidence sources, not truth |
| **Migration pain from legacy skills** | Existing skills break or become unreadable | Use compat mode with sidecar manifests |
| **Stale project memory** | Claims survive code changes incorrectly | Attach commit/file/symbol anchors + invalidation rules |
| **Concurrency conflicts** | Multiple runs patch the same skill/claim unpredictably | Use optimistic versioning and proposal queues |
| **Eval brittleness** | Good updates get rejected, bad updates slip through | Start with a small golden task set and conservative acceptance |
| **Operational sprawl** | Self-hosting multiple backends becomes a tax sink | Defer self-hosted providers until local core proves value |

### What parts of Hermes to preserve unchanged

Preserve Hermes’ distribution and operator shell: CLI, gateways, tool discovery, session search ergonomics, approval machinery, and skill hygiene/scanning. Preserve the conceptual distinction between built-in curated memory and episodic recall, but replace the underlying truth model. Preserve the curator as a **proposal generator**, not as the authority that changes state directly. Keep the memory-provider boundary as an ingestion/advisory interface, but stop letting providers define the system’s epistemology. citeturn14search11turn14search16turn14search17turn17search0turn17search2turn13search15turn6view0
